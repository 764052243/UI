## 一、当前用户实图指向的错误，不应再归咎于“没有PSD”

用户本轮并排提交：已处理的底部业务模块截图、资源目录、独立底座PNG，以及**最后一张已认可的完整大屏原图**。反馈聚焦：
- **底部五组蓝色发光立体底座**：重新切图/重绘后角度、透视或倾斜方向不一致，不能靠图片居中修。
- **亮蓝发光边缘和底座侧壁**：被矩形蒙版/紧裁截断，仅剩一半的光晕或立体厚度，不能只通过bbox/Alpha紧裁认定合格。
- **图标周围黑边/黑块**：可能是从暗背景抠图产生的预乘Alpha污染，也可能是原设计真实的黑色实体侧壁；必须对照金样与透明棋盘/白底/暗底分别判断，**不能一键去黑，也不能留整块暗色面板**。
- 高清生成是必要条件，但不能代替**形体、坐标、旋转/透视、光晕、底座光影和实际DOM组合**与原图一致。

**现有可直接读取的用户文件**：本轮挂载了`image.png`（1680×945整张截图，RGBA但所有像素Alpha=255）及`deco_business_plinth_shared.png`（132×102，RGBA，有效Alpha bbox 为(2,29)～(130,100)）。这能证明该底托层的几何留白和分辨率，但不能从一个扁平合成图唯一恢复所有光晕或被遮挡像素。用户在聊天里说“最后一张是原图”，必须以用户明确指向的最后一张作为**唯一金样**，不得因为文件名碰巧同名或挂载顺序而把其他版本误当认可原稿。

## 二、根因修复的操作优先级（HG0～HG6）

| 门禁 | 002必须实际执行 | 强制拒绝 |
|---|---|---|
| **HG0 认可原图 + 独立ROI** | 锁定最后一张原图；对五个业务单元分别圈定**完整图标+底托+光晕**的ROI和目标HTML显示位置，保存同视口截图基线 | 用第一次失败切图或局部截图当金样 |
| **HG1 几何重建而非低清扩放** | 独立glyph可SVG描摹，底托用**统一的可编辑透视几何源**生成，固定每个平行边、角点、厚度、高光方向与倾斜角；可复用一套底座 | 同一底托五个不同倾角、压扁/变宽/拉伸、仅滤镜增强旧132×102截图 |
| **HG2 分离真实三类内容** | 纯glyph、真实立体**几何实体**（包括暗色侧壁）、软阴影/外发光单独图层；纯黑页面背景用CSS或underlay不切PNG | 把整个暗色面板抠到PNG、或把合法黑色侧壁当脏边一键去除 |
| **HG3 有效Alpha与足够安全边** | 从可编辑SVG/3D按最终尺寸/DPR重新导出；软光层需要足够外扩画布。检查**所有非零Alpha**，不得把弱光当背景杂色裁掉；组件的`layer_anchor`坐标要保留，不能对每层做自动紧裁后无依据重新居中 | 边缘Alpha碰画布导致光晕齐切；对底托使用独立icon的2px紧裁规则而错位 |
| **HG4 排查黑边根因** | 先区分原图合法暗面与污染。若暗底抠图造成半透明边缘RGB变黑，回SVG/3D真透明源重新渲染，或用正确的straight/premultiplied Alpha颜色处理及精修蒙版。硬边防锯齿、软光不截断，100%/400%黑白棋盘复核 | 全黑转透明、整图羽化变糊、边缘残留锯齿/黑色矩形 |
| **HG5 HTML原坐标复合** | 底托、glyph、辉光按**统一视觉单元坐标系**合成，浏览器HTML中验证图层层级、scale、transform-origin、重心、视觉角度与金样保持一致 | 单张PNG看来居中但页面里旋转、错位、缺层 |
| **HG6 金样量化+人工双审** | 使用下面`audit_visual_unit_composite.py`的**认可金样+同视口隐藏该组件的underlay+实物PNG及定位**复合ROI检查，输出Gold/Composed/Diff；同时人工评审100%/400%边缘与原金样立体光影。修复后再整页HTML比对 | 平均RGB接近即宣称通过、只提供透明PNG却不提供真实浏览器组合 |

## 三、为什么旧的bbox脚本一再漏检

- **仅Alpha框居中**：一个底托侧壁黑色面积很大，居中检测会把它算进图像，无法验证透视/倾角是否与原图相同。
- **仅清理透明空白**：已被低清遮罩裁断的光晕**不可能靠缩小画布恢复**；必须返回矢量光源、蒙版或重建光影。
- **只比整页RGB均值**：底部单个100×100组件缺半块，在全页1680×945中占比很小，平均分数可能仍显得不错；应**逐个业务图形ROI、同位置、同DPR**评估。
- **整体黑底看起来与大屏融合**：黑色底板已经烘焙到PNG时在暗背景下可能不明显，换成浅色背景就暴露问题；但黑色侧壁属于原设计时则不得误删。
- **普通图标自动裁边 ≠ 立体底托正确定位**：`normalize_ui_icons.py`只针对需要独立紧裁的**前景icon符号**。带空间锚点的底座、辉光和完整复合单元**禁止未经对照进行自动裁边/居中**。

## 四、可执行的ROI复合验证（新）

工具：[**audit_visual_unit_composite.py**](../scripts/audit_visual_unit_composite.py)。用户原图和实际PNG均仅在002的本地私有交付目录使用，不上传公共UI仓库。

需要三项真实输入：
1. `gold_reference`：用户**最后一张认可原图**（未改动）。
2. `underlay_without_units`：相同视口、相同DPR、背景/其它UI不变，仅**目标底托+glyph+发光隐藏**后实际浏览器截图；不得用纯黑图代替完整复杂背景。
3. `visual_units[].layers`：完整视觉单元真实PNG图层与其在整页截图的**实际像素坐标**，不得为测试临时改变定位或scale。

配置示例（**纯说明，所有坐标/阈值非本轮用户真实测量**）：

```json
{
  "schema_version": "1.0",
  "reference_id": "user-approved-last-image",
  "gold_reference": "reference/approved.png",
  "underlay_without_units": "preview/browser-underlay.png",
  "visual_units": [{
    "id": "bottom-logistics",
    "roi": [100, 700, 210, 810],
    "pixel_tolerance": 16,
    "max_changed_fraction": 0.1,
    "max_mean_rgb_difference": 12,
    "layers": [
      {"path": "assets/components/plinth.png", "at_xy": [110, 745]},
      {"path": "assets/icons/truck.png", "at_xy": [138, 716]}
    ]
  }]
}
```

```bash
python scripts/audit_visual_unit_composite.py delivery/visual-unit-plan.json \
  --root delivery \
  --proof-sheet working/visual-unit-proof.png \
  --report working/visual-unit-qa.json
```

新脚本只**真实Alpha叠加**，不自动重采样、裁切、重定位或补色；对于疑似截断光晕（PNG Alpha贴边、小于2px安全边）输出FAIL；图层有效像素超出预设ROI会FAIL；与认可ROI的RGB差异超出**事先固定**的阈值则FAIL。生成`GOLD | COMPOSED | DIFF`证据图。

**注意**：ROI颜色一致性需要真实干净的underlay作为对照；若缺少同视口背景，应明确`未验证`，不能用黑底代替。自动阈值也不能证明原设计立体材质完全一致，最后还要人工验收造型、光影、黑边、锯齿。所谓`intentional_bleed`只能引用真实用户认可边界作为例外，不允许任意开关绕过图层边缘丢光问题。
