# SKILL｜复杂 UI 设计分层工作法（Instant 优先）V1.0

> 适用：UI设计师001业务系统、UI设计师002数据大屏。本 SKILL **不承诺**某模型档位质量必然不下降；将复杂决策外化为可检查的约束、版本、分阶段产物与验收。
> 顺序：**用户本轮明确指令/认可基线 → UI_DESIGN_CONVENTION.md → design-requirement-understanding → 本 SKILL + 对应专业 SKILL**。本 SKILL 不替代大屏/系统的专业知识。
> 配套方法与测试：`docs/COMPLEX_DESIGN_METHOD.md` 与 `docs/COMPLEX_DESIGN_REGRESSION.md`（从仓库根目录定位）。复杂任务才按需展开；简单任务不要重复加载整套长文档。

## 1. 何时触发与分级

符合**任一**条件即为复杂：①跨两个以上页面/状态；②两张以上不同用途参考图；③严格1:1且含材质/细字/复杂图形；④视觉稿、源码及交互同时要求；⑤大屏有多指标/数据关系或多分辨率；⑥多版本锁定、连续纠错、多个方案；⑦约束间存在真实冲突。它们不一定都需要问用户或分多轮，只需加强内部设计检查。

- C1 局部但有风险：单个区域涉及已锁基线、参考图或代码联动；按第2～5节做轻量控制。
- C2 多约束：多图、多状态、多页面或视觉与功能并存；建立可追溯的页面任务卡并分阶段验收。
- C3 高保真/高风险：严格还原、复杂大屏数据、连续失败或多状态源码；必须保存可证实基线、逐项验证关键约束，必要时建议用户在界面选更高思考档位，**不声称已自行切换**。

## 2. A：先冻结事实，生成最小“设计任务契约”

在内部或项目任务记录中维护一张**短卡**，仅随改动更新，不反复要求用户填写：

```text
任务/版本：目标页与待交付产物
输入证据：用户本轮文字、附件真实顺序、指定参考用途、上次认可图/文件
必须保留：布局｜配色｜材质｜业务字段｜交互｜非目标页面
允许改变：用户点名的页面/区域/维度
禁止重现：用户否定的本质造型、错误版本、未经授权的元素
本轮验收：可检查的视觉/数据/交互/文件目标与必要证据
未知风险：无法确认的来源或真实冲突（最多问一个改变结果的问题）
```

**事实、假设、建议严格分开**：用户明确的要求不可当设计师建议；未给的数据、模块、权限、业务流程不能写成事实。跨轮“第二张、上面/下面/继续”先回溯附件批次和当前目标页。用户问“为什么留白”是咨询，不能擅自出新图；用户说“修留白，颜色不动”则布局可动、颜色冻结。

## 3. B：拆成“依赖图”，不是一口气造完整大稿

以最小可验证单元拆解：**业务/数据语义 → 信息架构 → 页面骨架 → 视觉语言 → 组件/状态 → 交互或图表 → 交付**。选择 1 条主决策路径，完成每一步才进入后续；不要一次混改布局、色彩、材质和数据。

- 001 系统设计：角色/业务目标 → 页面地图与入口 → 导航与模块比例 → 表单/表格/状态 → 视觉/交互 → 实际源码。
- 002 大屏设计：观看场景/数据口径 → 指标权重与关系 → 主构图/图表类型 → 单位/图例/告警 → 颜色/空间与动效 → 屏幕/数据验证。
- **严格还原例外**：以原图为唯一“依赖图”；不提出另一套布局或自动简化材质。分辨率变化优先背景延展，不重排原图主体。
- **风格菜单例外**：只有用户明确「选择风格」才先展示 F01—F12 独立视觉参考；用户未选之前不出正式业务设计；不将内部结构候选误当作风格菜单。

可在内部比较两个有**结构差异**的合法方案，按业务完成度与基线符合度确定主方案；用户只要一个方案时交付一个，不强行增加问答或多张图。需要用户选择多个独立方向时才分别完整制作，不能仅换色冒充多方案。

## 4. C：按可视化关口推进，先骨架后精修

**关口G0—约束准确**：目标、图片身份、参考用途、锁定项和禁止项都已确认（可内部完成）。不准确就停止重绘/修改。

**关口G1—信息与布局**：确认业务内容完整、区域分配、视线动线、留白与模块比例合理；系统交互路径能解释、大屏数据关系真实。不要靠渐变、波浪、轨道、地图或发光填补结构错误。

**关口G2—造型与精细视觉**：颜色、层级、空间、材质、字重、字距、图标、光源、深浅关系分别检查。已认可配色不动；已认可整图不改其他区域。先看实际设计图/渲染，再说是否正确，不能以文字宣称已遵守。

**关口G3—组件与行为**：001 检查长菜单、左右切换、侧栏展开/折叠、空/错/加载/禁用、权限及提交反馈；002 检查坐标、单位、阈值、告警、图例、时间、实时或模拟标识。没有源码就不能声称交互已实现。

**关口G4—交付与回归**：一页一张完整图、正确尺寸/数量、真实资源、ZIP完整性、HTML实际运行和交互检查；只做过的测试才能报告通过，用户端下载未验证必须注明。汇总为 Q0～Q3 的证据，不另外给用户一堆重复检查表。

**G2/G4 补充硬门禁：高清与无关设计不动。** 凡输出设计图或修改已认可稿，额外加载 [高清与锁定区域保护 SKILL](../visual-fidelity-lock/SKILL.md)，实际检查最终完整PNG的尺寸、100%细节清晰度和原认可稿的非目标区域差异。文字乱码/模糊、输出只是缩略图、改动无关模块都不得通过；像素检查脚本仅证明文件与指定冻结区域，不能替代视觉审美检查。

高风险关口未通过，**只回退到最近可核验的已认可阶段修复**，不把失败图当新基线，不因“赶进度”跳过。单轮能完成所有步骤就直接完整交付；任务过大可自然分里程碑，不声称后台持续工作。

## 5. D：工具与修改策略（防止“感觉还原”）

1. 先查可编辑源文件或原始图、其尺寸与完整性。**能精准编辑即编辑原资源**；若只有截图、生成工具无法保证其余像素不变，说明“重建候选，不是精准修改”，不得谎称1:1。
2. 用户点名一处只改一处：代码需查看源文件、依赖和未提交改动，限制 CSS/DOM/JS 影响范围；图像修改需对照修改前后，核对非目标区域。不可逆覆盖、强推、合并他人分支都需按正式权限与安全边界执行。
3. 有数据图表需保留数据来源/单位/口径；无真实数据标注模拟。页面交互不能以静态预览冒充运行效果。
4. 出图后真正检查图：标题/图标/业务元素不丢失，材质与色彩不漂移，主体不裁切，留白真实改善。没有实际视觉比对则不称“视觉对照通过”。
5. 验证失败必须转成下一轮**未通过项**，记录“错在哪里/受影响区域/应恢复基线/下次验收证据”；每次只修失败原因，除非用户授权重做。

## 6. 复杂设计的最小交付协议

用户没有要求中间说明时，不要用大段“我将怎样思考”代替设计。必要的对外沟通控制为：**（一）本轮目标+冻结范围（仅歧义高时）→（二）设计图/源码或实际文件 →（三）通过与未通过证据**。不输出隐含推理过程；可以输出简短可检验决策依据。

复杂任务若原图不可访问、参考来源不清、缺少真实数据、运行条件不支持时应明示风险与已完成范围，不虚构成功率、速度、像素一致率。

## 7. 采用前回归而非口头保证

对应 `docs/COMPLEX_DESIGN_REGRESSION.md` 的 CD-01～CD-12，覆盖多图冲突、长会话锁定、业务系统多状态、复杂大屏、严格还原、改错维度、视觉稿与源码一致、文件/ZIP完整。文档静态校验只能证明**规则存在且可读**；只有在001/002的真实 Instant 任务中输入相同素材并检查实际产物，才能证明某个场景通过。用户认可决定最终视觉基线。
