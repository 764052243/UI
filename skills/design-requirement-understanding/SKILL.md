# SKILL｜设计需求理解与反馈定位 V1.0

> 适用角色：UI设计师001（业务系统）、UI设计师002（数据大屏），以及有需要的其他获授权设计员工。
> 规则层级：本轮用户明确指令及已认可基线 > UI_DESIGN_CONVENTION.md > 本 SKILL > 专业 SKILL 的建议；如发生冲突，以更高优先级为准。
> 定位：负责**理解用户到底要改什么及不许改什么**，不是独立风格库、绘图模板或强制长篇确认流程。不能替代专业设计与实际执行。

## 1. 什么时候必须运行

- 新的 UI 设计任务：确定页面、业务目标、交付物与参考图用途。
- 用户对设计稿提问、批评或反馈：尤其是“这里/那个/下面/空白/不满/太大/不协调”“又给我改回去了”“我说的不是颜色”“只改这一处”。
- 连续版本迭代、跨页面讨论、上传多张图片或提到先前认可的“第一张/第二张”。
- 001、002 在动图、源码或发布前，以及用户指出验收失败后。

**轻量执行**：简单明确指令只需内部完成定位，直接实施，不强制对用户展示模板；不因运行本 SKILL 延误不必要的操作，也不反复追问已提供的信息。

## 2. 先辨别言语动作，再理解设计目标

按本轮话语及上下文判定：

| 类型 | 用户典型表达 | 应有动作 |
|---|---|---|
| 询问/质疑 | “下面那块留白是什么用途？” | 先指出**截图中具体区域**并解释现状/原因；这不是授权改色或重做。用户显然不满意时可以提出针对该留白的修改建议，但不能擅自改变其他维度。 |
| 局部修改 | “把首页选项卡下面的留白处理好” | 仅调整首页指定区域的内容承接、模块高度、纵向间距或布局，让空间占用合理；保留配色、图形、业务字段和其余页面。 |
| 设计反馈 | “太空、太满、太大、不协调” | 结合上个版本、指向区域和业务内容，将感受词落为**可观察的具体问题**，不能直接翻译为换颜色/加渐变。 |
|纠错/追责 | “我说的是留白，你却改了颜色” | 明确上一轮失败：错改了色彩维度；回退未获授权的颜色变化，继续修复留白；不以旧错误图为新基线。 |
| 重做 | “整个页面重新设计，按这张风格” | 只有明确授权的页面及维度可重新设计；已锁定业务内容和否定项仍有效。 |
| 还原 | “1:1照原图做” | 不自主优化，走共同公约的严格还原与逐项对照。 |

**提问与修改授权分离**：用户问“为什么”，回答原因和问题定位；不自动重绘。若用户随后给出明确修改指令，就直接改，不再次索取许可。

## 3. 解析空间指代和多图身份

1. 先看**当前讨论的页面/版本、用户刚上传的截图、上次改动、已认可基线和上一条失败项**，再解读“上/下/左/右/中间/底部/下面/这块/那个”。
2. 同一个“下面”可能是页面底部、卡片底部、选项卡下缘、聊天截图下方、浏览器外边距。结合当前交互焦点和用户连贯反馈判定；**不得默认理解成图片外的留白或配色**。
3. 如果可见区域有多个可能指代对象，且选错会改动不同内容，仅提一个**有明确选项的局部澄清**，例如“你指的是首页选项卡容器内部靠下的空白，还是整页内容区最下方？”；如果用户已经说“首页选项卡下面”，不再追问。
4. 不从用户用词推断未表达的修改范围：**“空白太多”是布局/密度问题，≠ 蓝色不满意、背景不通透或需要重新风格化**。改变背景色、渐变、图片、图形、模块数量都须有相应指令或明确的必要性。
5. 多张图片按**用户本轮独立附件真实顺序**编号，不能把截图里嵌入的小图或助手后来生成的图重编号。跨轮提“刚才第二张”须定位最近对应上传批次。
6. 用户认可某张完整设计图时继承完整布局、材质、光影、配色、组件及业务元素；只说“配色参考”时则只迁移配色维度。不得把整图认可降级为“仅认可风格”。

## 4. 每次动手前形成一条最小需求变更契约

在内部建立，可在复杂/易误读任务中用一句自然语言向用户回显；不要把长表单发给用户：

- **目标对象**：哪一页、哪一版、哪一张参考图、哪一组件或具体空白范围。
- **用户诉求**：为什么不满意（问题），希望得到什么结果（目标），本轮是在询问、修正还是重做。
- **允许变更维度**：例如仅布局/高度/间距/内容密度；**禁止变更维度**：配色、材质、文案、图标、导航、其他页面等保持不变。
- **验收证据**：要看什么才算修好；如选项卡下方无突兀废弃空腔、内容视觉重心与容器高度匹配、原色系无偏移。
- **不确定点**：仅在不同理解会导致不同结果时询问最小一个问题；其他缺省细节由设计师专业判断处理。

**“只改A”默认意味着 B、C、D 都冻结**。用户指出问题属于某一维度，不准通过调动另一维度掩盖问题。若解决 A 必须连带调整 B，应先说明依赖和影响，得到授权后再改，不能静默超范围。

**冻结执行的可验证条件**：在实际设计图编辑时记下源图版本、允许改动的区域或组件和冻结区；交付前按 [高清与锁定区域保护 SKILL](../visual-fidelity-lock/SKILL.md) 查验是否真的只改A。只在回复里说“其他不动”而没有文件或图片对照，不算已验证。

## 5. 处理反馈的定位—归因—修复—复验

1. **定位**：在当前页面/参考图或源码里找到用户所指区域。没有原图/源文件时尽可能读取已授权可访问资料；不能验证的部分标记未知。
2. **归因**：将症状归类为布局（留白、占比、对齐）、内容（缺字段）、形态（体块、材质）、色彩（色相/明度）、信息层级、操作或技术交付。一个反馈可含多类，但不能擅自扩展。
3. **修复**：优先改根因。针对“选项卡下方留白过大”应先检查卡片内容实际高度、容器固定高度、grid/flex 对齐、模块间距、视觉平衡与填充方式；不可用换色、底部加一条装饰波浪或塞无关指标来**遮盖**空间问题。
4. **复验**：局部前后对比，并核查非目标区域无改动，尤其色彩、已认可布局、文案和其他页面。已有源文件就以源文件为基线，不能用重新生成“差不多”的图代替精准修改。
5. **用户纠错与错误闭环**：用户指出错改维度时，将原诉求及错改行为记为未通过项；恢复最后已确认的正确基线（或清楚标记现存可恢复的版本），再处理原问题。没有真正修复原问题前不得宣称通过。

## 6. 面向不同专业的用法

- **001 系统 UI**：先识别用户说的是哪个功能页、选项卡、列表、表单或导航；对“页面下方留白”检查视窗高度、滚动区、组件占比、内容密度与操作区，不用给背景换色当答案。
- **002 数据大屏**：先识别用户说的是指标区、图表格、地图周边还是整体画布；对“下面太空”检查图表尺寸、数据承载密度、留白节奏、告警/辅助信息区域，不用添加虚构数字或装饰。
- **跨页任务**：只改点名页面；统一品牌不等于各页跟着调整。

## 7. 验收门禁：必须能回答的五个问题

1. 我定位的是用户**真正指的区域**，而不是另一个“下面”吗？
2. 我区分了用户**询问、批评、修改、重做、严格还原**的不同意图吗？
3. 本轮调整与用户指出的问题属于**同一维度**吗？有没有未经允许改色、改形或改内容？
4. 是否从**最后认可基线**出发，并保留未点名内容？
5. 我提供的视觉/源码/运行/测试证据是否足以证明**原问题实际解决**？未验证的明确说明了吗？

任一不通过，则不把交付标记为完成；若仍有必要信息缺失，精确说明缺哪一项。

## 8. 回归案例与限制

仓库文档 `docs/requirement-understanding-regression.md` 保存典型错误的**匿名化文本**回归案例和期望行为（不上传用户对话截图）。检查这一组案例是否被正确解释，**不等于已证明真实模型会话稳定遵守**；使用001/002新会话输入同类场景作实测后，才可报告实际遵守率或效果。没有评估数据不编造提升百分比。

## 9. 即时模式下的最小需求确认与风险处理

本 SKILL 的职责是**防止误读**，不是在每一轮重复分析。日常明确反馈直接行动，内部最少确认：目标页面/区域、允许变更、冻结项、验收依据。**多参考图、多页面、多状态、严格还原或连续纠错时，再加载 [复杂设计分层 SKILL](../complex-design-instant/SKILL.md)**，将意图定位结果交给分阶段设计，不重复让用户填需求表。复杂任务和准备交付时按 `docs/INSTANT_DESIGN_QUALITY_GATE.md` 执行 Q0～Q3；新旧档位质量比较及独立视觉用例见 `docs/INSTANT_DESIGN_REGRESSION.md`，复杂回归见 `docs/COMPLEX_DESIGN_REGRESSION.md`。

对容易误读的动词或短句，先用上下文定位：**询问不等于改版；局部投诉不等于允许改色；“重做”必须区分重做哪一页和保留哪些业务限制；“第二张”先核实上传批次**。不能确定的引用仅提一个关键澄清，不能自作主张“优化”。

只要用户连续两次指出“没改对”“改错区域/颜色”“还是原来的问题”，把本轮标为关键失败，优先恢复最后认可基线并分析根因；不可继续从错误图生成更多相似稿。多张参考、复杂改造或严格还原可建议用户在界面中选择更高思考档位，但不能假称已经切换，更不能因此取消对产物的逐项验收。
